# 游戏编程与数值计算领域区别

## 我是游戏程序员，介绍一下，哪些领域要用到数值计算？比如气象领域？还有呢？

气象确实是数值计算最典型的领域之一。简单说：

  > 当现实问题由连续的物理量、方程、测量数据组成，而计算机只能用有限的浮点数进行近似计算时，通常就需要数值计算。

  它关注的不是普通业务程序里的增删改查，而是：

  - 方程怎么近似求解
  - 误差有多大
  - 计算是否稳定
  - 几十亿次运算怎样高效完成
  - 结果是否收敛、是否可信

  ## 气象预报具体在算什么？

  可以把大气划分成大量三维小格子。每个格子保存：

  struct AirCell {
      double temperature;
      double pressure;
      double humidity;
      Vec3 windVelocity;
  };

  物理定律描述了每个格子如何影响周围格子，例如：

  - 空气从高压区流向低压区
  - 热量在相邻区域传播
  - 水汽凝结并释放热量
  - 地球自转影响风向
  - 地形改变空气流动

  程序从当前状态开始，反复计算：

  当前大气状态
      ↓ 模拟未来 10 秒
  新的大气状态
      ↓ 再模拟 10 秒
  更新的大气状态
      ↓
  不断推进到未来几天

  真实模型包含数亿乃至更多网格数据，因此必须使用超级计算机并行计算。这里既有物理建模，也有大量线性代数、微分方程和误差控制。

  ## 其实游戏也一直在做数值计算

  你可能没有使用过被称作“数值计算库”的东西，但游戏开发中经常在做同类工作：

  ### 物理模拟

  velocity += acceleration * dt;
  position += velocity * dt;

  这实际上是在用离散时间步近似求解微分方程，通常称为数值积分。

  Euler、Verlet、RK4 都属于数值计算方法。

  ### 碰撞和约束求解

  刚体系统要处理：

  - 接触约束
  - 摩擦力
  - 关节约束
  - 穿透修正

  物理引擎内部经常需要求解大型方程组或迭代求解约束。

  ### 图形学

  常见的：

  clipPosition = projection * view * model * position;

  就是线性代数。蒙皮、光照、光线追踪、降噪、流体和布料模拟也包含大量数值计算。

  ### 动画和曲线

  - 线性插值
  - 三次样条
  - 四元数插值
  - 逆向运动学
  - 动画混合

  这些都属于数值计算的一部分。

  ### 导航和 AI

  路径搜索本身偏离散算法，但下面这些更接近数值计算：

  - 转向行为
  - 轨迹优化
  - 神经网络推理
  - 概率估计
  - 群体运动模拟

  ## 为什么游戏程序员很少直接使用传统数值库？

  因为游戏需要的数值功能，通常已经被包装在更专门的系统里：

  - glm、DirectXMath：向量和矩阵
  - Unreal/Unity 数学类型
  - PhysX、Havok、Box2D：物理计算
  - Bullet：刚体和碰撞
  - GPU shader：大规模 SIMD 计算
  - Eigen：偶尔用于工具链、优化或几何处理

  游戏还有一些特殊要求：

  - 必须在一帧时间内完成
  - 通常更重视视觉可信，而不是科学精度
  - 数据结构要适合缓存和 SIMD
  - 可能要求跨平台确定性
  - 允许使用近似算法换取速度

  而科学计算可能愿意运行几个小时甚至几天，但要求误差有依据、结果能够验证。

  ## 数值计算的几个核心类别

  掌握下面这张“地图”，基本就能理解大部分数值库在做什么：

  1. 线性代数
     向量、矩阵、线性方程组、特征值。

  2. 数值积分
     模拟物体、流体、轨道等状态随时间的变化。

  3. 微分方程
     描述热量、空气、水流、电磁场如何变化。

  4. 优化
     在大量可能性中寻找损失最小或收益最大的方案。

  5. 插值与拟合
     根据有限采样点估计曲线或模型。

  6. 傅里叶变换和信号处理
     分析声音、图像、振动和通信信号。

  7. 随机模拟
     使用随机采样估计难以直接计算的问题，例如 Monte Carlo。

  所以，游戏开发不是没有数值计算，而是使用了一个非常专业化、强调实时性的数值计算子集。你写过矩阵变换、物理积分、插值、IK、shader 或粒子模拟，就已经接触过数值计算，只是通常不会把它单独叫作“科学计算”。


› 你说的强调实时性的数值计算子集，展开说说


• 我说的“强调实时性的数值计算子集”不是一个正式学科名称，更准确地说是：

  > 游戏选择了一批适合实时预算、允许近似、结果视觉可信的数值方法。

  科学计算常问：“这个结果误差是多少、是否收敛？”

  游戏开发更常问：“这一帧能不能算完、画面看起来对不对、会不会突然爆炸？”

  ## 实时性改变了什么？

  60 FPS 时，每帧总预算约为：

  1000 ms / 60 ≈ 16.67 ms

  但这 16.67 ms 还要分给：

  - 游戏逻辑
  - 动画
  - 物理
  - AI
  - 渲染提交
  - 音频
  - 操作系统和驱动

  物理模拟可能只能使用其中几毫秒。因此游戏中的数值方法通常要满足：

  - 计算时间有明确上限
  - 不能偶尔突然算几百毫秒
  - 允许牺牲精度
  - 结果需要稳定
  - 容易 SIMD、GPU 或多线程并行
  - 错误最好“不容易被玩家看出来”

  这会直接影响算法选择。

  ## 1. 时间积分：从速度计算位置

  游戏里最常见的数值计算之一：

  velocity += acceleration * dt;
  position += velocity * dt;

  物理公式其实描述的是连续变化：

  [
  \frac{dx}{dt}=v,\qquad \frac{dv}{dt}=a
  ]

  但计算机只能每隔一小段时间更新一次，所以只能近似。

  ### 显式 Euler

  position += velocity * dt;
  velocity += acceleration * dt;

  简单、便宜，但对弹簧等系统容易不稳定。

  ### 半隐式 Euler

  velocity += acceleration * dt;
  position += velocity * dt;

  只是交换一下顺序，稳定性通常就会更好。许多实时物理系统会使用类似方法。

  ### 更高精度的方法

  例如 RK4，需要在一步中多次计算：

  估计一次
  估计第二次
  估计第三次
  估计第四次
  综合四次结果

  它可能更精确，但计算量更大。在某些轨迹预测、相机运动或工具中很合适，却未必适合成千上万个实时刚体。

  因此，游戏经常选择：

  > 精度没那么高，但便宜、稳定、行为可预测的方法。

  ———

  ## 2. 固定时间步：用确定的频率模拟世界

  如果直接使用每帧时间：

  simulate(frameDeltaTime);

  一旦帧率变化，数值误差和物理行为也可能变化。游戏常使用固定时间步：

  constexpr float fixedDt = 1.0f / 60.0f;

  accumulator += frameDeltaTime;

  while (accumulator >= fixedDt) {
      simulate(fixedDt);
      accumulator -= fixedDt;
  }

  它带来几个好处：

  - 数值行为更稳定
  - 更容易调试
  - 不同帧率下物理更加一致
  - 对回放和网络同步更友好

  但如果游戏卡顿，积累了大量未模拟时间，就可能出现著名的“死亡螺旋”：

  模拟没算完
    ↓
  下一帧更慢
    ↓
  需要补算更多物理步骤
    ↓
  变得更慢

  所以实际程序还会限制：

  frameDeltaTime = std::min(frameDeltaTime, 0.25f);

  或者限制每帧最多补算多少次。

  这是一种非常有游戏特色的取舍：宁愿丢掉一些物理时间，也不能让程序无限追赶。

  ———

  ## 3. 碰撞约束：不追求一次得到精确解

  假设一个箱子放在地面上。从数学上说，需要同时满足：

  - 箱子不能穿过地面
  - 地面对箱子产生支撑力
  - 摩擦力不能超过一定范围
  - 多个箱子之间互相影响
  - 关节必须保持连接

  大量物体堆叠后，会形成一个很大的约束求解问题。

  理论上可以建立大型方程组并求出高精度解。但实时物理引擎通常采用迭代法：

  for (int iteration = 0; iteration < 8; ++iteration) {
      for (Contact& contact : contacts) {
          solveContact(contact);
      }
  }

  只迭代固定次数，例如 4、8 或 16 次。

  这意味着结果未必完全收敛，但运行时间可控：

  更少迭代：
  快，但堆叠可能抖动、下陷

  更多迭代：
  更稳定，但更耗时

  游戏一般不会说“必须求到误差小于 (10^{-12})”，而是说“8 次迭代看起来已经足够稳”。

  这种思想常出现在：

  - Sequential Impulse
  - Gauss–Seidel 迭代
  - Position-Based Dynamics
  - XPBD
  - 布料和绳索约束

  ———

  ## 4. Position-Based Dynamics：直接修位置

  严格的物理模拟通常先计算力，再计算加速度、速度和位置：

  力 → 加速度 → 速度 → 位置

  而游戏里的布料、绳索和头发常采用更直接的方法：

  预测位置
    ↓
  检查约束
    ↓
  把违反约束的位置拉回来

  例如两点之间的绳子应该保持固定长度：

  Vec3 delta = p2 - p1;
  float error = length(delta) - restLength;

  Vec3 correction = normalize(delta) * error * 0.5f;
  p1 += correction;
  p2 -= correction;

  反复执行几次，绳子就大致恢复正确长度。

  这不一定严格还原真实世界的受力过程，但优点很适合游戏：

  - 不容易爆炸
  - 容易控制
  - 可以直接表达“这两个点不能分开”
  - 计算量可以用迭代次数控制
  - 视觉效果通常足够好

  ———

  ## 5. 稳定性往往比精度更重要

  假设有两个算法：

  - 算法 A：正常情况下误差只有 0.01%，但偶尔数值爆炸
  - 算法 B：始终有 2% 误差，但永远稳定

  科学计算可能会认真研究怎样修复 A；实时游戏往往更愿意先选择 B。

  游戏中常见的稳定性处理包括：

  ### 限制速度

  velocity = clampLength(velocity, maxSpeed);

  ### 限制时间步

  dt = std::min(dt, maxDt);

  ### 添加阻尼

  velocity *= 0.98f;

  ### 增加子步

  for (int i = 0; i < 4; ++i) {
      simulate(dt / 4.0f);
  }

  ### 修正穿透

  position += normal * penetrationDepth;

  ### 让静止物体休眠

  if (velocity.lengthSquared() < threshold) {
      body.sleep();
  }

  其中一些做法并不“数学优雅”，但非常实用。

  ———

  ## 6. 低精度数据通常已经足够

  科学计算经常使用：

  double  // 64 位浮点数

  游戏大量使用：

  float   // 32 位浮点数

  GPU 中还会使用：

  16 位浮点数
  混合精度
  压缩后的整数格式

  原因包括：

  - 内存占用更小
  - 缓存利用率更好
  - SIMD 一次处理更多数据
  - GPU 吞吐量更高
  - 画面未必能体现额外精度

  但 float 的有效数字有限。当世界坐标很大时：

  Vec3 position{1000000.0f, 0.0f, 0.0f};
  position.x += 0.001f;

  这个微小变化可能无法表示。

  因此大型世界需要：

  - 浮动原点
  - 分区坐标
  - 相机相对坐标
  - CPU 用 double、GPU 用 float
  - 高低位拆分

  这也是典型的游戏数值问题：不是算法不会写，而是浮点数的精度和世界尺度发生了冲突。

  ———

  ## 7. LOD 不只用于模型，也用于计算

  游戏会根据重要程度调整数值计算精度。

  例如远处的物体可能：

  - 使用更低频率更新
  - 使用更简单的碰撞体
  - 减少物理迭代次数
  - 不模拟内部关节
  - 直接播放预制动画
  - 完全进入休眠

  流体也可能从高精度三维计算退化为：

  - 二维表面波
  - 顶点动画
  - 法线贴图
  - 粒子效果
  - shader 中的程序化噪声

  也就是说，游戏不一定要算出真实的水，而是要生成玩家认为像水的结果。

  ———

  ## 8. 渲染也是实时数值计算

  实时渲染中充满近似。

  ### 光照积分

  真实的像素颜色涉及对大量光线路径进行积分。离线电影渲染可以每像素采样成百上千次，游戏可能每像素只有几个样本，甚至一个样本。

  于是需要：

  - 时间累积
  - 空间滤波
  - 降噪
  - 重要性采样
  - 历史帧重投影
  - 各种近似光照模型

  实时光线追踪的核心思路之一就是：

  少量昂贵样本
  +
  复用过去和邻近像素的信息
  +
  降噪
  =
  视觉上可接受的图像

  它算出的未必是严格正确的光照，但在运动的画面里看起来足够可信。

  ### 阴影

  真实阴影需要处理复杂的可见性积分，而游戏可能使用：

  - Shadow Map
  - PCF
  - VSM
  - 屏幕空间阴影
  - 级联阴影贴图

  这些都在精度、稳定性、带宽和帧时间之间取舍。

  ———

  ## 9. 插值是游戏中非常重要的数值工具

  游戏中很多连续效果，实际只有有限采样点。

  position = lerp(previous, current, alpha);
  rotation = slerp(previousRotation, currentRotation, alpha);

  常见用途包括：

  - 动画关键帧
  - 网络位置平滑
  - 固定物理步与渲染帧之间的平滑
  - 相机运动
  - 曲线和轨迹
  - 参数渐变

  网络游戏收到的位置是离散的：

  t0：玩家在这里
  t1：玩家在那里

  渲染端通过插值生成中间状态。这不是真实计算出玩家每个时刻的位置，而是构造一个视觉连续的近似。

  外推则是根据速度预测尚未收到的状态：

  predictedPosition = lastPosition + velocity * elapsed;

  这也是数值计算，只不过它服务的是延迟隐藏。

  ———

  ## 10. 游戏追求可预测的耗时

  某些科学算法使用自适应终止条件：

  while (error > tolerance) {
      iterate();
  }

  问题是，它可能迭代 3 次，也可能迭代 3000 次。对于实时帧预算，这很危险。

  游戏更喜欢：

  for (int i = 0; i < 8; ++i) {
      iterate();
  }

  结果可能没有充分收敛，但最坏耗时容易估计。

  因此游戏算法经常偏爱：

  - 固定迭代次数
  - 固定内存容量
  - 固定时间步
  - 有上限的任务数量
  - 超出预算时降级
  - 跨帧分摊计算

  “最坏情况会发生什么”通常比“平均速度多快”更重要。

  ———

  ## 11. 实时性、确定性和并行性之间还有冲突

  游戏希望使用多线程、SIMD 和 GPU，但浮点运算不满足严格结合律：

  (a + b) + c

  不一定等于：

  a + (b + c)

  并行归约改变运算顺序后，结果可能产生微小差异。这些差异在物理模拟里经过很多帧可能逐渐放大。

  所以不同游戏会选择不同策略：

  - 单机视觉效果：允许小差异，尽量并行
  - 锁步网络游戏：高度重视确定性
  - 服务器权威游戏：客户端允许近似，服务器决定最终结果
  - 回放系统：记录输入、状态或关键帧进行纠正

  这里的挑战不只是“算得快”，还包括“不同机器是否算出同样结果”。

  ———

  ## 科学模拟和游戏模拟的典型区别

  以水为例：

   科学计算                          游戏
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━
   关注压力、速度等物理量是否准确    关注水看起来是否真实
  ────────────────────────────────  ──────────────────────────
   进行网格收敛性分析                根据性能选择网格分辨率
  ────────────────────────────────  ──────────────────────────
   记录误差和边界条件                用阻尼和限制防止爆炸
  ────────────────────────────────  ──────────────────────────
   可以运行几小时                    每帧必须在几毫秒内完成
  ────────────────────────────────  ──────────────────────────
   可能使用双精度                    通常使用单精度甚至半精度
  ────────────────────────────────  ──────────────────────────
   结果用于工程决策                  结果用于玩家体验

  不过两者并非绝对分开。例如赛车和飞行模拟器，可能比一般游戏更重视物理真实性；影视特效虽然不实时，却可能不要求严格的科学准确性。

  ## 游戏程序员最值得掌握的数值知识

  如果从游戏开发出发，比较实用的学习顺序是：

  1. 浮点数误差
     精度、范围、epsilon、绝对误差与相对误差。

  2. 向量和矩阵
     坐标变换、基变换、投影、逆矩阵。

  3. 四元数和插值
     lerp、slerp、样条曲线。

  4. 数值积分
     Euler、半隐式 Euler、Verlet、RK 方法。

  5. 稳定性与时间步
     固定步长、子步、刚性系统。

  6. 迭代求解器
     接触、关节、IK、布料约束。

  7. 优化问题
     IK、轨迹、参数拟合。

  8. 信号与滤波
     相机平滑、输入处理、动画和网络状态平滑。

  归根结底，游戏中的实时数值计算有一个非常鲜明的目标：

  > 在严格的时间和硬件预算内，用可控的近似产生稳定、可信、对玩家有意义的结果。

  它不是简单地把科学计算“做低配”，而是针对感知、交互和实时反馈重新选择了评价标准。
